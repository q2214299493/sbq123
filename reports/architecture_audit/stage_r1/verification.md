## Exact review method and limitations

- Enumerated the baseline with `git ls-tree -rz --name-only <baseline> scripts modules configs tests` and read every tracked Python file in those roots with Python source encoding detection and parsed each with `ast`. The report table records definitions, forward and reverse import edges, static side-effect signals and longest function spans. No claim is made about the implementation of every external skill, native executable or vendored archive.
- Resolved absolute/relative `import` and `from` statements, including imports inside functions, against tracked in-scope Python module names. Computed strongly connected components across 1,134 directed edges in non-archive implementation. Dynamic imports, CLI command strings, Python path injection, shell/Node entry points and external consumers require manual review. The dependency graph combines observed imports and labeled scientific handoffs. Syntax/AST inventory covered every file. Human review focused on ownership entry points, cross-layer dependencies, gates, major hotspots and cited Stage A/B evidence. It was neither line-by-line formal verification nor proof of live safety or scientific accuracy.
- Source code and tracked schema/config were read from the publication worktree. Project state docs establish recorded projection status only. For historical native capability we used archived receipts/output and existing independent-reference tests. R.1 did not execute native engines, open or mutate a production SQLite for scientific validation, query any live scheduler or run compute, alter the original evidence, approve State Handoff or enter a new stage. Existing live scientific status and runtime installation remain outside scope.
- Local verification used Windows, `C:/Anaconda/python.exe` 3.13.9 and pytest 8.4.2. Both invocations used cache-disabled pytest, selected explicit files and cleared `SBQ_ZACROS_BENCHMARK_EXE`, `SBQ_MKM_NATIVE_APPROVAL_SOURCE` and `SBQ_MKM_NATIVE_RUN_ROOT` from the child shell.
